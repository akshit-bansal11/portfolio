## In one minute

- A **rate limiter** checks every request against a limit, like "100 per minute per API key". Under the limit: let it in. Over: make it wait, or turn it away with **429** and a **Retry-After**.
- It protects your servers, keeps things fair between customers, slows down abuse and caps what expensive requests cost you.
- Five classic ways to count: **fixed window** (simple, leaks at the edges), **sliding log** (exact, memory-hungry), **sliding counter** (a cheap, near-exact estimate), **token bucket** (a steady average plus short bursts) and **leaky bucket** (a smooth, constant output).
- On many servers the counters live in **Redis** and are updated **atomically**. Good clients **back off with jitter**. When requests differ hugely in size, limit by **cost**, not by count.

## Why every API needs a limiter

<Callout kind="real-world" title="The turnstiles at rush hour">

A big metro interchange at 9 a.m.: thousands of people pour down the stairs, and a row of turnstiles lets them through one at a time, at a steady pace. When the crowd is too big, the queue forms at the gates, not as a crush on the platform edge. The gates aren't there to annoy anyone. They control the *rate* at which people get in, because the platform can only safely hold so many.

- One customer ships a script with a bug in a `while` loop. It calls your API a few thousand times a second.
- Your servers slow down, then fall over, and every other customer goes down with them.
- That runaway script is the 9 a.m. crowd, and you have no turnstiles.

<Callout kind="note" title="Where the ideas came from">

- The **leaky bucket** is usually credited to Jonathan Turner's 1986 work on fast packet switching, where telecom engineers had to stop one sender flooding a shared link. The token bucket is its close cousin.
- **429 Too Many Requests** was standardised in RFC 6585 in 2012. `Retry-After` comes from HTTP itself.
- The IETF is working on standard **RateLimit** headers, so servers can tell clients their remaining quota *before* they hit the wall.

</Callout>

## How a limiter decides

Every rate limiter answers one question, many thousands of times a second: *a request from this key just arrived; let it in or not?*

The five classic algorithms differ only in step 3: what they remember, and how they count.

### 1. Fixed window counter

- Count requests per key in fixed blocks of time: 10:00–10:01, 10:01–10:02, and so on.
- Under the limit: allow the request and add one. When a new block starts, reset to zero.
- Tiny, fast and easy to understand.

```ts
const windowStart = Math.floor(now / 60_000);        // which minute is it?
const count = (counters.get(key + windowStart) ?? 0) + 1;
counters.set(key + windowStart, count);
return count <= LIMIT;                                // allow or reject
```

The famous flaw is the boundary. Fire the burst below, then switch to the sliding log to see the fix.

  <WindowBoundary />
</Figure>

### 2. Sliding window log

Instead of counting per block, remember the **timestamp** of every accepted request.

<Flow
  steps={[
    { title: "Request at 10:00:40", note: "look up this key's log", tone: "blue", icon: <Clock /> },
    { title: "Drop old stamps", note: "anything before 09:59:40", tone: "red", icon: <Trash2 /> },
    { title: "Count what's left", note: "stamps in the last 60 s", tone: "amber", icon: <ListOrdered /> },
    { title: "Under the limit?", note: "yes: allow and log the stamp", tone: "green", icon: <ShieldCheck /> },
  ]}
/>

- **Exact.** The window slides with time, so there is no boundary trick.
- **Memory-hungry.** With a limit of 10,000 requests per hour, you might store 10,000 timestamps for *each* key. Across millions of users, that adds up.

### 3. Sliding window counter

A clever compromise: keep just two counters per key, this window and the previous one. Then *estimate* the last full window by weighting the previous window by how much of it the frame still covers.

```ts
// 15 s into the current minute, the previous minute still overlaps by 45 s (75%).
const estimate = previousCount * 0.75 + currentCount;
return estimate < LIMIT;
```

<Figure caption="Limit: 10 per minute. The amber frame is the last 60 seconds. The estimate assumes the previous minute's requests were spread evenly, so it multiplies their count by the overlap. Drag the slider and compare it with the exact count.">
  <SlidingCounter />
</Figure>

- It assumes the previous window's requests were spread evenly. That is rarely exactly true, but close enough at scale.
- Cloudflare uses this approach, and found the estimate wrong for only a tiny fraction of requests (case file #3).

### 4. Token bucket

A tap refills a bucket with tokens at a steady rate, say 2 per second, up to a maximum of 5. Every request must take one token. No token, no entry, until the tap drips in another.

<DemoFrame
  title="Token bucket"
  hint="try Burst ×8"
  caption="Refills 2 tokens a second, holds 5. A full bucket lets a burst of 5 straight through; after that, requests only get in as fast as tokens drip in. When the bucket is full, new drips spill away."
>
  <BucketSim kind="token" />
</DemoFrame>

Two knobs, and that's its superpower:

- The **refill rate** sets the long-run average (2 per second).
- The **capacity** sets how big a burst you tolerate (5 at once).
- A page that fires 5 requests on load sails through. A script trying 50 per second is cut down to 2.

>
  Your building has a rooftop tank that refills from the mains at a steady trickle. In the morning, five flats shower at once and it's fine, because the tank was full. But if everyone runs taps all day, the tank empties and stays nearly empty: you only get as much as the trickle provides.
</Analogy>

### 5. Leaky bucket

The leaky bucket flips the picture. Requests pour *into* a bucket (a queue) and leak *out* of the bottom at a fixed rate.

<DemoFrame
  title="Leaky bucket"
  hint="try Burst ×8"
  caption="Holds 5, leaks 2 a second. A burst waits in the bucket (202, with its wait time) and drains at a steady pace. Only when the bucket is full do extras get 429."
>
  <BucketSim kind="leaky" />
</DemoFrame>

- A burst isn't served instantly. It is **smoothed out** into a steady stream.
- That is exactly what you want when the thing behind the limiter (a database, a payment network, an SMS provider) can only handle a constant pace.
- The bucket has a *maximum* size. Without one, the queue would grow without end.
- Shopify's REST Admin API is a real leaky bucket (case file #4).

## Where should the limit live?

You can limit in three places, and real systems usually use all three.

- **Client-side.** Doesn't protect you from bad clients, but makes good ones much easier to live with.
- **At the gateway or edge.** The cheapest place to stop a flood (more in the [traffic patterns post](/blog/traffic-patterns)).
- **In the service.** Only the service knows what a request *means*, so fine-grained limits live here.

A polite client, in code:

```ts
// Polite client: respect Retry-After, otherwise back off exponentially with jitter.
async function callWithRetry(request: () => Promise<Response>, attempt = 0): Promise<Response> {
  const response = await request();
  if (response.status !== 429 || attempt >= 5) return response;
  const retryAfter = Number(response.headers.get("Retry-After"));
  const backoff = Number.isFinite(retryAfter) && retryAfter > 0 ? retryAfter * 1000 : 2 ** attempt * 500;
  await new Promise((resolve) => setTimeout(resolve, backoff + Math.random() * 250));
  return callWithRetry(request, attempt + 1);
}
```

```lua
-- KEYS[1] = bucket key; ARGV = capacity, refill per second, now (seconds)
local bucket = redis.call("HMGET", KEYS[1], "tokens", "ts")
local capacity, rate, now = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])
local tokens = tonumber(bucket[1]) or capacity
local last = tonumber(bucket[2]) or now
tokens = math.min(capacity, tokens + (now - last) * rate)
local allowed = tokens >= 1
if allowed then tokens = tokens - 1 end
redis.call("HSET", KEYS[1], "tokens", tokens, "ts", now)
redis.call("EXPIRE", KEYS[1], math.ceil(capacity / rate) * 2)
return allowed and 1 or 0
```

## Saying "slow down" politely

A good rejection is specific and useful:

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 2
Content-Type: application/json

{ "error": "rate_limited", "message": "Too many requests. Try again in 2 seconds." }
```

- **Say when.** `Retry-After` tells well-behaved clients exactly how long to wait.
- **Say how much is left.** Many APIs also send headers on *every* response, such as requests remaining and when the quota resets, so clients slow down before they hit the wall. GitHub does this (case file #2).

<Callout kind="real-world">

It's the metro display that says "next train in 2 min". People wait calmly when they know how long.

</Callout>

### When requests differ in size, count cost

Counting requests treats a tiny lookup and a giant query the same. For GraphQL, where one query can ask for one field or ten thousand, that's a poor fit.

- **Shopify** limits its GraphQL Admin API by calculated query cost (case file #4).
- **GitHub's** GraphQL API also uses a points-based limit instead of a plain request count.
- Fairer and better at protecting the servers when request sizes vary wildly; harder to build and to explain.

<Callout kind="tip">

Not every endpoint deserves the same limit. Match the limit to the cost and risk of each one: heavy data and order placement tighter, cheap lookups looser. Zerodha does exactly this (case file #5).

</Callout>
