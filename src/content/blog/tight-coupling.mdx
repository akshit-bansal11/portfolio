## In one minute

- **Coupling** is how much one part of a system has to know about another. The test: if I change or break A, how many other parts change or break with it?
- Tight coupling is fairy lights wired in series: one dead bulb and the whole string goes dark. Loose coupling is parallel wiring: each part fails alone.
- Two kinds, two fixes. **Interfaces** stop *changes* spreading. **Events and queues**, plus timeouts and fallbacks, stop *failures* spreading.
- Splitting code into services is not the same as decoupling it. Amazon, Segment, Shopify, Uber and Zerodha each found that the right number of boxes is the fewest that keep a change in one place.

## The night the whole tree went dark

If you grew up with old fairy lights for Christmas or Diwali, you know the ritual: plug in the string, nothing happens, then test every bulb to find the one dead one.

- Many older strings were wired in **series**. Current had one path: through bulb one, bulb two, bulb three, to the end and back.
- One burned-out filament broke that path, so every bulb went dark.
- Modern strings work around it. Many mini-lights have a tiny shunt in each bulb that lets current skip a dead filament, and better strings wire bulbs in **parallel**, so each bulb has its own path to power.

Software does this too. A small, boring part fails or changes, and the checkout page, the mobile app and the nightly report all break with it. Engineers call "these parts are wired in series" **tight coupling**.

<Callout kind="insight">

The fix isn't "never connect things". It's "connect them through the right kind of socket".

</Callout>

## What coupling is

Every module needs some others. Checkout needs payments, payments needs a bank. That's fine: software is parts working together. Coupling is about *how much* each part has to know about the others.

<Callout kind="important" title="The coupling test">

If I change or break module A, how many other modules have to change or break with it? "None, as long as A keeps its promises" means loose. "Let me search the whole codebase" means tight.

</Callout>

### Cohesion: the sibling idea

- Coupling is about the lines *between* modules. Cohesion is about what's *inside* one.
- A `PaymentService` that only handles payments has high cohesion. A `utils.ts` that formats dates, sends emails and calculates GST has low cohesion: it's a junk drawer.
- The two are linked. Scatter related code across modules and those modules have to keep talking. Keep it together and most conversations stay inside one module.
- Hence the old slogan: **low coupling, high cohesion**.

## Where the idea came from

The idea is old, and it keeps coming back at a bigger scale.

  steps={[

- **Larry Constantine**'s ideas reached a wide audience through the 1974 *IBM Systems Journal* paper "Structured Design" by Wayne Stevens, Glenford Myers and Constantine. It gave the two properties the names that stuck: coupling and cohesion.
- **David Parnas**'s 1972 paper "On the Criteria To Be Used in Decomposing Systems into Modules" took one small program, a keyword index generator, and split it into modules two ways.

<Callout kind="insight" title="Information hiding">

Split a system by **what is likely to change**, and hide each of those decisions behind an interface. Almost every loose-coupling technique in this post is this one idea. Object-oriented languages made it private fields; microservices made it separate services that own their data.

</Callout>

## How loose coupling works

A tiny online store: Checkout needs to reserve stock in Inventory. Here are three ways to wire that, from tightest to loosest. Pick one, then break things.

### Step 1: spot the secret

Ask Parnas's question: what about Inventory is likely to change?

- How stock is stored: a table today, maybe a separate warehouse system tomorrow.
- How reservations expire.
- Which warehouse fulfils which pin code.

Those are Inventory's secrets. Nobody else should depend on them. Here's the tightly coupled version, where Checkout knows Inventory's table names and column meanings:

```ts
// file: checkout.ts
// Tightly coupled: Checkout knows Inventory's tables.
const row = await db.query(
  "SELECT qty FROM inventory_stock WHERE sku = $1 AND warehouse_id = 3",
  [sku],
);
if (row.qty < quantity) throw new Error("Out of stock");
await db.query("UPDATE inventory_stock SET qty = qty - $1 WHERE sku = $2", [quantity, sku]);
```

- If Inventory renames `qty`, adds a second warehouse or moves to another database, Checkout breaks.
- So do the three other modules that copied this snippet.

### Step 2: put the secret behind an interface

An **interface** is a promise: "ask me these questions, in this shape, and I'll answer in this shape."

```ts
// file: inventory/index.ts
// The only thing other modules may import.
export interface Inventory {
  reserve(sku: string, quantity: number): Promise<{ ok: boolean; reservationId?: string }>;
}

// checkout.ts: loosely coupled
const result = await inventory.reserve(sku, quantity);
if (!result.ok) return showOutOfStock(sku);
```

- Checkout now knows one function and two fields. Inventory can rewrite everything behind `reserve()` and Checkout never notices. That's the LEGO stud.
- It's also a step down the ladder: Checkout passes just a `sku` and a `quantity` (data coupling), not a whole `Order` (stamp coupling) or a `mode` flag (control coupling).

<Callout kind="important">

The interface is the *only* thing you promise not to break. Everything behind it is yours to change.

</Callout>

### Step 3: don't wait when you don't have to

Interfaces fix change-time coupling. Run-time coupling needs one more idea.

- When an order is placed, a lot should happen: ship the parcel, email a receipt, update analytics, adjust stock.
- Checkout doesn't need to wait for any of that before saying "order confirmed". It only needs payment to succeed.
- So it publishes one **event** and moves on.

```ts
// file: checkout.ts
await payments.charge(order.total); // the one thing we must wait for
await bus.publish({ type: "OrderPlaced", orderId: order.id, items: order.items });
return confirm(order);

// email/worker.ts: a separate module that listens
bus.subscribe("OrderPlaced", async (event) => {
  await sendReceipt(event.orderId);
});
```

- If the email service is down for ten minutes, its notes wait on the board, and it catches up when it's back.
- That's the parallel wiring from the fairy lights. One dead bulb doesn't kill the string.

### Step 4: for calls you must make, plan for failure

Some calls really are synchronous: you can't confirm an order without charging the card. For those, loose coupling means not trusting the other side to always be there.

## Other ways to untangle things

Interfaces plus events is the default toolkit, not the only one. Each alternative has an everyday picture and a real cost.

### Keep it glued, on purpose

<Analogy title="A sandwich">
  Nobody builds a modular sandwich with a standard bread-to-filling interface. It's small, you eat it in five minutes, and you'll never swap the cheese mid-bite. Gluing it together is the right call.
</Analogy>

A 200-line script, a prototype, or a function that does one job doesn't need interfaces between its parts. Tight coupling *inside* a small, cohesive unit is fine; it's *between* units that it hurts.

### Share one database

<Analogy title="The office fridge">
  Everyone keeps lunch in one shared fridge. No deliveries, no asking, just open the door. Until someone reorganises the shelves "to make it tidier", three lunches go missing, and nobody knows whose fault it is.
</Analogy>

Several apps read and write the same database. It's fast to build and works while you're small.

### Split everything into microservices

<Analogy title="Everyone moves into their own house">
  Housemates who keep fighting each buy a separate house. Now nobody touches your stuff. But borrowing a cup of sugar means a car trip, and planning dinner takes a group call.
</Analogy>

Microservices enforce boundaries physically: you can't reach into another service's memory, because it's on another machine.

### A modular monolith

<Analogy title="One apartment building, locked doors">
  Everyone lives in one building, with one address, one lift and one maintenance team. But each flat has a locked door, and if you want something from your neighbour, you knock.
</Analogy>

One deployable app. Modules may only use each other's public APIs, and a check in CI fails the build when someone sneaks around them.

### Abstract everything, just in case

<Analogy title="A house where every wall is on wheels">
  Every wall rolls, so you can redesign any room any time. In practice nothing feels solid, and you spend your weekends rolling walls around instead of living in the house.
</Analogy>

Interfaces, plugin systems, factories, adapters and config flags for changes that might never come.

### Which one, when

<Callout kind="note">

Microservices fix *organisational* coupling (teams blocking each other) more than *code* coupling. Splitting code into services does not, by itself, decouple anything.

</Callout>

<Callout kind="tip" title="Don't abstract on a guess">

Sandi Metz, in her 2016 post "The Wrong Abstraction": duplication is far cheaper than the wrong abstraction. A practical rule: wait until you've written something three times before abstracting it, because by then you know what actually varies.

</Callout>

### When the "alternative" wins

Sometimes the less fashionable option is the better choice, and good teams say so out loud:

- **Segment** moved *back* from well over a hundred microservices to a single service, because the boundaries cost them more than they protected.
- **Shopify** chose a modular monolith over microservices for its core app, and built tooling to enforce boundaries inside one codebase.
- **Zerodha**, one of India's largest stockbrokers, publicly argues for keeping systems simple and avoiding complexity for its own sake.
- Martin Fowler's "MonolithFirst": most successful microservice systems he's seen started as monoliths that were split once the right boundaries became clear.

<Callout kind="important">

The goal was never "more boxes". The goal is that **a change in one place stays in one place**, with the fewest boxes that achieve it.

</Callout>

2. D. L. Parnas, ["On the Criteria To Be Used in Decomposing Systems into Modules"](https://doi.org/10.1145/361598.361623), *Communications of the ACM* 15(12), 1972.
3. Steve Yegge, ["Stevey's Google Platforms Rant"](https://courses.cs.washington.edu/courses/cse452/22wi/papers/yegge-platform-rant.html), 2011 (archived copy).
4. Jim Gray and Werner Vogels, ["A Conversation with Werner Vogels"](https://queue.acm.org/detail.cfm?id=1142065), *ACM Queue* 4(4), 2006. Summary with excerpts: [InfoQ](https://www.infoq.com/news/Amazon-CTO-Werner-Vogels-on-SOA).
5. Alexandra Noonan, ["Goodbye Microservices: From 100s of problem children to 1 superstar"](https://www.twilio.com/en-us/blog/developers/best-practices/goodbye-microservices), Segment, 2018. Follow-up talk: [InfoQ, "To Microservices and Back Again"](https://www.infoq.com/news/2020/04/microservices-back-again/).
6. Kirsten Westeinde, ["Deconstructing the Monolith"](https://shopify.engineering/deconstructing-monolith-designing-software-maximizes-developer-productivity), Shopify Engineering, 2019.
7. Shopify Engineering, ["Enforcing Modularity in Rails Apps with Packwerk"](https://shopify.engineering/enforcing-modularity-rails-apps-packwerk), 2020.
8. Adam Gluck, ["Introducing Domain-Oriented Microservice Architecture"](https://www.uber.com/blog/microservice-architecture/), Uber Engineering, 2020.
9. Kailash Nadh, ["Scaling with common sense"](https://zerodha.tech/blog/scaling-with-common-sense/), Zerodha Tech, 2020, and ["Hello, World!"](https://zerodha.tech/blog/hello-world/), Zerodha Tech.
10. Sandi Metz, ["The Wrong Abstraction"](https://sandimetz.com/blog/2016/1/20/the-wrong-abstraction), 2016.
11. Martin Fowler, ["MonolithFirst"](https://martinfowler.com/bliki/MonolithFirst.html), 2015.
12. James Lewis and Martin Fowler, ["Microservices"](https://martinfowler.com/articles/microservices.html), 2014.
