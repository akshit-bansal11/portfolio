## In one minute

- Several people (or devices) edit the same data at once, sometimes offline. Every copy must end up the same, and nothing may be lost.
- **Last-write-wins** keeps the newest save and silently drops the rest. **Locking** avoids conflicts but kills offline editing.
- **OT** (Google Docs) rewrites each edit through one central server. **CRDTs** are data structures whose merges work in any order, so any device can sync with any other, with no referee.
- **Yjs**, a CRDT library: every insert gets a permanent ID, deletes leave tombstones, and sync sends only what the other side is missing. The price is extra metadata. If a server is always in the middle, a simpler design (like Figma's) can be enough.

## The grocery list in the basement

- Meera and Kabir share a grocery list app. On Saturday they split up in a big supermarket whose basement has no mobile signal.
- Meera adds "eggs". Two aisles away, Kabir adds "chai". Neither phone can reach the internet, so each saves its own version.
- Back upstairs, both phones sync. A simple sync sees that Kabir saved a minute later, and keeps Kabir's list.
- The eggs are gone. No error, no warning.

  <LostUpdateReplay />
</Figure>

<Callout kind="important">

Nobody did anything wrong. The sync rule threw the edit away. This is the core problem of collaboration software: **several people changing the same data at the same time**, sometimes offline, and everyone expecting the same sensible result. Google Docs, Figma, Notion, multiplayer code editors and collaborative canvases all have to solve it.

</Callout>

<Callout kind="note" title="The goal">

Everyone edits freely, offline or online. Every copy ends up identical. Nothing is lost, and nobody waits.

</Callout>

## The two easy answers, and why they fail

### Last-write-wins

- Keep the version with the latest timestamp. Used everywhere, often by accident.
- It converges, because everyone agrees on the winner. But it gets there by **throwing data away**: the lost update above.
- Fine where only the latest value matters: a profile photo, a "last seen" time.

<Callout kind="insight">

LWW **per field** is itself a valid CRDT. The basement sync is bad because it applies LWW to the *whole list*.

</Callout>

## Round 1: Operational Transformation

- **1989:** Clarence Ellis and Simon Gibbs publish OT, from research on software for groups.
- Describe every edit as an **operation**. When two happen concurrently, **transform** one against the other before applying it, so it still means what its author intended.

<Figure caption="Meera inserts at 5 while Kabir deletes at 2. By the time Meera's insert reaches Kabir, his text has shifted left by one. Flip Kabir's phone to 'applies it as sent' to see what goes wrong.">
  <OtTransformDemo />
</Figure>

- OT turned out to be very hard to get right for complex documents, especially with many users and no central coordinator.
- **1995:** Xerox PARC's **Jupiter** system made it manageable by routing every edit through a **central server**:

- Google Wave was built on ideas from Jupiter. **Google Docs** was built on OT with a central server (case file #1).

<Callout kind="warn" title="The catch">

OT needs that central server to referee. Offline for an hour? Your edits can't be properly merged until the server sees them. Long offline sessions and peer-to-peer syncing are hard to support.

</Callout>

## Round 2: CRDTs

- **2011:** Marc Shapiro, Nuno Preguiça, Carlos Baquero and Marek Zawirski formalise **Conflict-free Replicated Data Types**.
- Replicas update independently, in any order, and **always converge**. It's mathematically guaranteed, with no coordination.
- The trick is to design the data type so that merging is safe in every order:

<FeatureGrid
  items={[
    { title: "Commutative", tone: "violet", icon: <ArrowLeftRight />, tag: "merge(A, B) = merge(B, A)", text: "Merging A then B gives the same result as B then A." },
    { title: "Associative", tone: "blue", icon: <GroupIcon />, tag: "merge(merge(A, B), C) = merge(A, merge(B, C))", text: "It doesn't matter how you group merges." },
    { title: "Idempotent", tone: "green", icon: <CopyCheck />, tag: "merge(A, A) = A", text: "Merging the same thing twice is harmless." },
  ]}
/>

- With all three, it doesn't matter what order updates arrive in, whether they're delayed, or whether some arrive twice. Everyone ends up in the same place.

### The simplest CRDT: a grow-only counter

- Say you count "likes" across phones. Instead of one number, each replica keeps **one slot per replica** and only increments its own.
- To merge, take the **maximum of each slot**. The total is the sum of the slots.

<Figure caption="Like on either phone, then merge in any order, any number of times. Both phones always land on the same slots and the same total.">
  <CounterMerge />
</Figure>

<Callout kind="insight" title="Why max, not add?">

Adding would count the same likes again every time a merge arrived twice. Taking the max is idempotent, and it never goes backwards, because each slot only grows.

</Callout>

<Quiz
  question="The network retries, and phone B receives the same merge from phone A twice. Which property makes that harmless?"
  options={["Commutative", "Associative", "Idempotent", "None: B now double-counts"]}
  answer={2}
>

Idempotent means merging the same state twice changes nothing. Max of (3, 3) is still 3.

</Quiz>

## How Yjs works

- **Yjs** is an open-source CRDT library for JavaScript, created by Kevin Jahns.
- It's based on **YATA**, an algorithm described in a 2016 paper by Nicolaescu, Jahns, Derntl and Klamma.
- You use shared types that look like normal data structures (`Y.Text`, `Y.Array`, `Y.Map`), and Yjs handles the merging.

### Step 1: every insert gets a permanent ID

- Text editing is the hard case. "Insert at position 5" breaks as soon as someone else edits before position 5: you just saw it in the OT demo.
- So Yjs doesn't use positions at all. Every inserted character (or list item) becomes an **item** with:
  - a unique ID: **who** created it (a random client ID) and **their counter** (0, 1, 2…);
  - a reference to the item it was inserted **after** (and before), at the moment it was typed.
- "Insert 'i' after item `A:2`" means the same thing on every replica, whatever else has changed.

<Figure caption="How Yjs builds the word 'chai': a chain of items, each with a (client, counter) ID and a link to its neighbour. The deleted 'y' stays in the chain as a tombstone, and that's what lets a late edit land in the right place.">
  <YjsItemChain />
</Figure>

### Step 2: inserts at the same spot get the same order everywhere

- Meera and Kabir both insert right after "bread" at the same time. Both new items point to the **same neighbour**.
- Yjs breaks the tie with rules every replica applies the same way, based on the items' IDs and origins.
- Neither item is lost. The order is just consistent everywhere.

### Step 3: deletes leave tombstones

- When you delete an item, Yjs doesn't throw it away. It marks it deleted: a **tombstone**.
- Why: an edit from an offline phone might still say "insert after item `B:0`". If `B:0` were gone, nobody would know where to put the new text.
- Yjs keeps just enough of deleted items for this, and works hard to keep tombstones small, for example by merging runs of consecutive items into one.

<Quiz
  question="Why does Yjs keep a deleted item as a tombstone instead of removing it straight away?"
  options={["So the user can undo the delete", "So edits that point at the deleted item still know where they go", "Because JavaScript can't free memory", "To make documents bigger on purpose"]}
  answer={1}
>

Items are placed by "after item X", not by position. If X vanished, a late edit that says "after X" would have nowhere to go. In the chain above, "i" lands after the tombstone B:0.

</Quiz>

### Step 4: sync by asking "what haven't you seen?"

- Every Yjs document keeps a **state vector**: for each client, the highest counter it has seen. "I have everything from client A up to 12, and from B up to 7."
- To sync, a replica sends its state vector. The other side replies with exactly the missing items.
- That's how a phone that's been offline for a day catches up quickly. It works the same through a server, directly between browsers, or even by passing a file around.

<Figure caption="Each square is one item. The phone sends a few numbers; only the items the other side lacks travel back, in both directions.">
  <StateVectorSync />
</Figure>

In code, that's all it takes to merge two documents:

```ts
// file: merge.ts
import * as Y from "yjs";

const meera = new Y.Doc();
const kabir = new Y.Doc();

meera.getArray("groceries").push(["eggs"]); // offline
kabir.getArray("groceries").push(["chai"]); // offline, at the same time

// Reconnect: each side sends exactly what the other is missing.
Y.applyUpdate(kabir, Y.encodeStateAsUpdate(meera, Y.encodeStateVector(kabir)));
Y.applyUpdate(meera, Y.encodeStateAsUpdate(kabir, Y.encodeStateVector(meera)));

meera.getArray("groceries").toArray(); // both items, in the same order on both phones
```

Things to try:

1. **Lost update.** Take both phones offline, add a different item on each, reconnect. Yjs keeps both; last-write-wins keeps only the newer phone's list.
2. **Back from the dead.** Offline, delete an item on one phone and tick it off on the other. Reconnect. Yjs keeps both intentions consistent everywhere. Last-write-wins either loses an edit or brings the deleted item back.
3. **The cost.** Watch the document size. It grows a little even when you delete things, because the history needed for merging is part of the data.

## Offline-first, for free

Because a CRDT doesn't need a referee, **offline stops being a special case**.

### When the simpler design wins

- **Figma**'s 2019 engineering post explains that the team looked at both OT and CRDTs, then built a system *inspired* by CRDTs but simpler, because Figma always has a central server.
- Each property on each object (a rectangle's colour, say) uses last-write-wins, and the server is the authority on the order of changes.
- A design file is a tree of objects with properties, not one long string of text. So per-property LWW gives the right behaviour almost everywhere, and the central server avoids much of the metadata a fully decentralised CRDT needs.
- **Google Docs** sticks with OT, which suits a world where every edit goes through Google's servers anyway.

<Callout kind="important" title="The lesson">

CRDTs shine when you want **offline-first, peer-to-peer, or no single referee**. If you always have a server in the middle, a simpler server-authoritative design can be the better trade.

</Callout>
