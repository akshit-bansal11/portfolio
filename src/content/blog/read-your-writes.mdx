## In one minute

- Your database cluster has one **primary** that takes every write and **replicas** that copy it a moment later. That moment is **replication lag**.
- Write to the primary, read from a replica before the copy arrives, and you get old data: a **stale read**. The ₹100 you just added "vanishes".
- The promise you want is **read-your-writes**: once *your* write succeeds, *your* reads always include it. Other people can be a beat behind.
- Fixes, from simplest to most precise: return the new value from the write itself, read the user's own data from the primary, stick to the primary for a few seconds, or carry a **version token** so reads only hit replicas that have caught up. Synchronous replication also works, at a price.

## The ₹0 shock

Here is the bug from the user's side. Three screens, a fraction of a second apart.

<WalletWireframe />

- **Nothing was lost.** The primary has ₹100. Replica 2 will have it in a moment.
- **It still looks broken.** For that moment, money vanished. In a payments app that means a support ticket, a second top-up (now they've paid twice), or an uninstall.
- **It's the same bug everywhere**: an edited profile that reverts on refresh, a comment that disappears after you post it, a "your order" page that says you have no orders.

<Callout kind="important">

Correct-but-late data is a bug when the person seeing it is the person who just changed it. "Eventually consistent" is fine for strangers, not for the author.

</Callout>

### Step through the race

The bug is a race between two things: the change travelling to the replica, and your read travelling to the replica. The read is a single hop. The change has to be shipped and replayed. The read often wins.

### Why replicas fall behind

Lag is not a fixed number. It is small most of the time and jumps when something is busy.

<Callout kind="insight">

Think of lag as a range, not a number. If it is usually a few milliseconds, a deploy, a backfill or a traffic spike can still push it to seconds. Your fix has to hold on the bad day, not the average one.

</Callout>

## Name it: read-your-writes

This guarantee has a name, and it comes from a 1994 paper by Doug Terry and colleagues at Xerox PARC on the Bayou system: **"Session Guarantees for Weakly Consistent Replicated Data"**. They noticed that users don't need *every* copy to be perfect. They need the system to never contradict what *they* already did or saw. They wrote down four such promises.

<Callout kind="note">

Read-your-writes is per user. If your friend checks your shared wallet one second later and sees the old number, that is usually acceptable. When it isn't (an approval step, a fraud check, stock control), that read needs the primary.

</Callout>

Things to try:

1. **Any node**, lag 1.5 s, press "Add + refresh" a few times. Roughly two refreshes in three hit a replica that hasn't caught up yet.
2. **Primary after a write**, set the window to 1 s and the lag to 2.5 s. The window expires before the replicas catch up, and the bug comes back.
3. **Version token**. Never stale, and reads go back to replicas as soon as one catches up. Check "reads on primary".
4. **Sync replication**. Never stale, but look at "last write took": every write now waits for the slowest replica.

## The fixes

### Fix 1: don't read at all

The cheapest read is the one you skip. The write already knows the new balance, so send it back.

```sql
-- file: add_money.sql
-- One round trip: change the balance and return the new value from the primary.
UPDATE wallets
SET balance = balance + $2
WHERE user_id = $1
RETURNING balance;
```

- The success screen shows the balance from this response, not from a fresh query.
- Pair it with **optimistic UI**: show "₹100 added" as soon as the server says OK, and keep that value on the device for the next screen.
- **Limit:** it only covers the screen that made the write. Reload, another tab, the transaction history, another device: all of those still read. You need one of the fixes below as well.

### Fix 2: read your own data from the primary

Split reads by whose data they are.

  <Node title="Incoming read" note="who owns this data?" tone="violet" icon={<Route />} />
  <Row>
    <Group title="The user's own data" tone="pink" icon={<KeyRound />}>
      <Node title="balance, transactions, profile" note="→ primary, always fresh" tone="pink" icon={<Database />} />
    </Group>
    <Group title="Everyone else's / shared data" tone="blue" icon={<Eye />}>

  </Row>

```ts
// file: db.ts
// The few queries that must see the user's latest writes are marked; the rest use replicas.
export function dbFor(read: { ownData: boolean }) {
  return read.ownData ? primary : pickReplica();
}

const wallet = await dbFor({ ownData: true }).query(
  "SELECT balance FROM wallets WHERE user_id = $1",
  [userId],
);
```

- **Cost:** the primary serves every "my data" read. For a wallet that is usually fine: a balance is one indexed row.
- **Breaks when** "my data" is most of your traffic. Then the replicas sit idle and the primary is the bottleneck again.

### Fix 3: stick to the primary for a while after a write

After a user writes, send *their* reads to the primary for a few seconds. After that, the replicas have almost certainly caught up.

<Flow
  steps={[
    { title: "User writes", note: "commit on primary", tone: "pink", icon: <PenLine /> },
    { title: "Remember when", note: "wrote:user = now, expires in 2 s", tone: "amber", icon: <Timer /> },
    { title: "Next read", note: "flag still there?", tone: "violet", icon: <Route /> },
    { title: "Yes → primary", note: "no → any replica", tone: "green", icon: <Split /> },
  ]}
/>

```ts
// file: sticky.ts
// The window must be longer than your worst realistic lag, not your average lag.
const WINDOW_MS = 2_000;

export async function afterWrite(userId: string) {
  // Kept per user in Redis (not a cookie), so it also covers the user's other devices.
  await redis.set(`wrote:${userId}`, "1", { PX: WINDOW_MS });
}

export async function dbForRead(userId: string) {
  return (await redis.exists(`wrote:${userId}`)) ? primary : pickReplica();
}
```

Rails has this built in (Rails 6 and later), with a 2-second default:

```ruby
# file: config/environments/production.rb
config.active_record.database_selector = { delay: 2.seconds }
config.active_record.database_resolver = ActiveRecord::Middleware::DatabaseSelector::Resolver
config.active_record.database_resolver_context = ActiveRecord::Middleware::DatabaseSelector::Resolver::Session
```

<Callout kind="warn">

The window is a guess about lag, not a measurement of it. If a migration pushes lag past the window, you're back to ₹0. Pair it with lag monitoring and take replicas that are too far behind out of the read pool.

</Callout>

### Fix 4: version tokens (the precise one)

Instead of guessing *how long* to wait, remember *how far* the primary had got when your write committed, and only read from a replica that has got at least that far.

<Flow
  steps={[
    { title: "Write", note: "commit on the primary", tone: "pink", icon: <PenLine /> },
    { title: "Read its position", note: "LSN 0/3A0 or a GTID", tone: "amber", icon: <ListOrdered /> },
    { title: "Save the token", note: "per user, in Redis", tone: "violet", icon: <KeyRound /> },
    { title: "Pick a replica", note: "replayed ≥ token?", tone: "blue", icon: <Route /> },
    { title: "None ready?", note: "wait a little or use the primary", tone: "green", icon: <ArrowRightLeft /> },
  ]}
/>

PostgreSQL, with node-postgres:

```ts
// file: wallet.ts
// 1. Write on the primary. With autocommit, the UPDATE has committed when it returns.
const { rows } = await primary.query(
  "UPDATE wallets SET balance = balance + $2 WHERE user_id = $1 RETURNING balance",
  [userId, 100],
);
// 2. Ask how far the primary's log has got. It is at or past our commit.
const { rows: pos } = await primary.query("SELECT pg_current_wal_insert_lsn() AS lsn");
await redis.set(`ryw:${userId}`, pos[0].lsn, { EX: 60 });

// 3. Later, for a read: use a replica that has replayed at least that far.
export async function dbForRead(userId: string) {
  const token = await redis.get(`ryw:${userId}`);
  if (!token) return pickReplica();
  for (const replica of shuffle(replicas)) {
    const { rows } = await replica.query(
      "SELECT pg_last_wal_replay_lsn() >= $1::pg_lsn AS fresh",
      [token],
    );
    if (rows[0].fresh) return replica;
  }
  return primary; // nobody has caught up yet
}
```

MySQL, with GTIDs. The replica can even *wait* for the change instead of refusing:

```sql
-- file: mysql_token.sql
-- On the primary, right after the write: which transactions have committed?
SELECT @@GLOBAL.gtid_executed;

-- On the replica, before the read: wait up to 1 second for that set.
-- Returns 0 when caught up (run the read here), 1 on timeout (use the primary).
SELECT WAIT_FOR_EXECUTED_GTID_SET('3E11FA47-71CA-11E1-9E33-C80AA9429562:1-77', 1);
```

MongoDB has the token built in, called a **causally consistent session**:

```js
// file: mongo.js
// Inside one session, reads see the session's earlier writes, even on a secondary.
const session = client.startSession({ causalConsistency: true });
const wallets = client.db("pay").collection("wallets");

await wallets.updateOne(
  { userId },
  { $inc: { balance: 100 } },
  { session, writeConcern: { w: "majority" } },
);
const wallet = await wallets.findOne(
  { userId },
  { session, readPreference: "secondary", readConcern: { level: "majority" } },
);
```

- Across HTTP requests, save the session's `operationTime` and `clusterTime`, and call `advanceOperationTime` and `advanceClusterTime` on the next request's session.
- **Cost:** one extra tiny query per read in the simple version. Routers avoid it by checking each replica's position a few times a second and keeping it in memory.
- **Breaks when** the token store is down. Then treat every read as "no token" or send it to the primary; never fail the request.

<Callout kind="tip">

Keep the *highest* token you've seen per user, from writes and reads. That gives you **monotonic reads** for free: a user can never bounce from a fresh replica to a staler one and watch their balance go backwards.

</Callout>

### Fix 5: synchronous replication

Make the primary wait until replicas have *applied* the change before it says OK. Then any replica you read from is fresh.

```ini
# file: postgresql.conf
# Wait for both standbys to replay the change before COMMIT returns.
synchronous_standby_names = 'FIRST 2 (replica1, replica2)'
synchronous_commit = remote_apply
```

<Compare
  label="synchronous_commit"
  columns={[{ title: "COMMIT returns after…", tone: "blue" }, { title: "Read-your-writes on the replica?", tone: "green" }]}
  rows={[
    ["off / local", "the primary alone has it", "No"],
    ["remote_write", "the standby received it (not yet on its disk)", "No"],
    ["on (with sync standbys)", "the standby saved it to disk", "No: saved is not yet replayed"],
    ["remote_apply", "the standby replayed it, so queries there can see it", "Yes"],
  ]}
/>

- **MySQL:** semi-synchronous replication is *not* enough. It waits for a replica to receive the change, not to apply it. Group Replication's `group_replication_consistency` setting (`BEFORE` or `AFTER`) is the one that gives fresh reads.
- **Cost:** every write now takes as long as the slowest synchronous replica. Cross-region, that is very noticeable.

<Callout kind="warn">

If a synchronous replica is slow or dead, writes slow down or stop until it is removed from the list. You've turned a read problem into a write-availability problem. Use synchronous replication when you need it for durability (no data loss on failover), not as your read-your-writes fix.

</Callout>

### Don't forget the cache

If you cache balances in Redis or Memcached, the cache is one more copy that can lag.

- On a write, update or delete the cached value in the same code path.
- Never fill the cache from a replica that is behind, or you'll freeze the stale value in place for the whole TTL. Facebook hit exactly this (case file #1).

<Callout kind="important" title="What I'd ship for a wallet">

1. Return the new balance from the write (fix 1).
2. Read the balance and transaction history from the primary (fix 2). They're the user's money and they're cheap indexed lookups.
3. Send everything else (offers, merchant lists, analytics) to replicas.
4. When primary read load becomes a real problem, move own-data reads to version tokens (fix 4).

</Callout>

<Callout kind="warn" title="Never approve a payment from a replica">

Read-your-writes is about what the user *sees*. Whether they can *spend* is a different question, and the answer must come from the primary, in the same statement that moves the money:

```sql
-- file: pay.sql
-- Checks and debits atomically on the primary. Zero rows updated = insufficient funds.
UPDATE wallets
SET balance = balance - $2
WHERE user_id = $1 AND balance >= $2
RETURNING balance;
```

</Callout>

## The 30-second interview answer

If someone asks you this exact wallet question, this order covers it:

1. **Name it.** Replication lag breaks *read-your-writes*, a per-user guarantee. You don't need global strong consistency.
2. **Skip the read.** Return the new balance from the write and show it straight away.
3. **Route by owner.** The user's own balance and transactions read from the primary; shared data reads from replicas.
4. **Scale with tokens.** Store the commit's LSN or GTID per user; read only from replicas that have replayed past it; otherwise wait briefly or use the primary.
5. **Trade-offs.** A time window (like Rails) is simpler but fails when lag spikes. `remote_apply` works but slows every write and can block writes.
6. **Operate it.** Monitor lag, eject lagging replicas, keep users on one replica, test with a delayed replica, and never approve a debit from a replica.
