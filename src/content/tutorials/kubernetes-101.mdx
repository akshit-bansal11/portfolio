## In one minute

<Logo tech="k8s" label className="text-2xl" />

- **Kubernetes** (K8s for short: K, then 8 letters, then s) runs containers across a group of machines.
- You write down what you want ("3 copies of my web app"), and it keeps that true, forever.
- If a container crashes or a machine dies, it starts a replacement by itself.
- It does not build images. Docker (or a similar tool) builds them; Kubernetes runs them.

<Callout kind="tip" title="Before this">

You should know what an image and a container are. If not, do [Docker 101](/tutorials/docker-101) first: its walkthrough builds the app we deploy here.

</Callout>

## A first manifest, explained

```yaml
# Annotated example, not the walkthrough file
apiVersion: apps/v1
kind: Deployment            # "keep N copies running"
metadata:
  name: web
spec:
  replicas: 3               # how many copies
  selector:
    matchLabels:
      app: web              # manage pods with this label
  template:                 # what each pod looks like
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: hits:1.0   # the image Docker built
          ports:
            - containerPort: 3000
---
apiVersion: v1
kind: Service               # one stable name in front of the pods
metadata:
  name: web
spec:
  selector:
    app: web                # send traffic to pods labelled app=web
  ports:
    - port: 80              # the Service's port
      targetPort: 3000      # the container's port
```

<Callout kind="insight">

Labels are the glue. The Deployment stamps `app: web` on every pod it makes, and the Service sends traffic to anything wearing `app: web`. Nothing refers to a pod by name or IP.

</Callout>

## When not to use Kubernetes

- One app or a few on one server: **Compose** is simpler.
- Nobody on the team will own upgrades, access rules and monitoring.
- A managed container service does the job: **Cloud Run, AWS ECS/Fargate, Azure Container Apps**.
- Small, steady traffic: autoscaling buys you nothing.

### Build the cluster and deploy

kind (Kubernetes in Docker) builds a real cluster whose nodes are Docker containers. That is why it is perfect for a laptop, and why, on Windows and macOS, the whole cluster ends up as containers inside Docker Desktop's hidden VM.

```yaml
# file: hits/k8s/kind.yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
  - role: worker
  - role: worker
```

The Redis file runs one Redis and gives it a Service named `redis`. It has no persistent volume, which is a deliberate shortcut and you will see its cost soon.

```yaml
# file: hits/k8s/redis.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: redis
spec:
  replicas: 1
  selector:
    matchLabels:
      app: redis
  template:
    metadata:
      labels:
        app: redis
    spec:
      containers:
        - name: redis
          image: redis:7-alpine
          ports:
            - containerPort: 6379
          resources:
            requests:
              cpu: 50m
              memory: 32Mi
            limits:
              memory: 128Mi
---
apiVersion: v1
kind: Service
metadata:
  name: redis
spec:
  selector:
    app: redis
  ports:
    - port: 6379
      targetPort: 6379
```

The web file has four things: a ConfigMap with the Redis address, a Deployment with three copies, probes and resource settings, and a Service that gives them one name. The rolling update settings mean "never remove a working pod before its replacement is ready".

```yaml
# file: hits/k8s/web.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: hits-config
data:
  REDIS_URL: redis://redis:6379
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: hits:1.0
          imagePullPolicy: IfNotPresent
          envFrom:
            - configMapRef:
                name: hits-config
          ports:
            - containerPort: 3000
          readinessProbe:
            httpGet:
              path: /healthz
              port: 3000
            periodSeconds: 3
          livenessProbe:
            httpGet:
              path: /healthz
              port: 3000
            initialDelaySeconds: 10
            periodSeconds: 10
          resources:
            requests:
              cpu: 50m
              memory: 64Mi
            limits:
              memory: 128Mi
---
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 3000
```

<Steps>
  <Step title="Create the cluster" tone="cyan" checkpoint="kind prints a few progress lines and ends with a message that you can now use your cluster. kubectl get nodes lists three nodes, all Ready (this can take a minute).">

The first run downloads a large node image, so be patient.

```bash
kind create cluster --name hits --config k8s/kind.yaml
kubectl get nodes
```

  </Step>
  <Step title="Get your image into the cluster" tone="cyan" checkpoint="kind prints that it loaded the image onto each node.">

The cluster's nodes cannot see the images on your Docker. Normally they would pull from a registry. For a local image, load it into the nodes.

```bash
kind load docker-image hits:1.0 --name hits
```

  </Step>
  <Step title="Apply the desired state" tone="cyan" checkpoint="After a short wait, rollout status says the deployment was successfully rolled out, and kubectl get pods shows three web pods and one redis pod, all Running and 1/1 Ready.">

```bash
kubectl apply -f k8s/redis.yaml -f k8s/web.yaml
kubectl get pods --watch
```

Press Ctrl+C once everything is Running, then:

```bash
kubectl rollout status deployment/web
kubectl get pods
```

  </Step>
  <Step title="Open a door to the Service" tone="cyan" checkpoint="The port-forward command stays running and prints Forwarding from 127.0.0.1:8081. In a second terminal the curl prints hits with a version of 1.0.">

`port-forward` is a temporary tunnel from your laptop to the Service. It is for debugging, not for production. Run it in one terminal and leave it running, and curl from another.

```bash
kubectl port-forward service/web 8081:80
```

```bash
curl http://localhost:8081
```

Notice the "served by" name is always the same pod: the tunnel picked one pod when it started. To see the Service spreading load, ask from inside the cluster instead.

```bash
kubectl exec deploy/web -- wget -T 5 -qO- http://web
kubectl exec deploy/web -- wget -T 5 -qO- http://web
kubectl exec deploy/web -- wget -T 5 -qO- http://web
```

  </Step>
  <Step title="Scale it" tone="cyan" checkpoint="Five web pods are listed and become Ready within a few seconds. Scaling back to three terminates two.">

```bash
kubectl scale deployment/web --replicas=5
kubectl get pods
kubectl scale deployment/web --replicas=3
```

  </Step>
  <Step title="Kill a pod and watch it come back" tone="cyan" checkpoint="The pod you deleted goes Terminating, and a new pod with a different suffix appears right away. The count stays at three.">

Pick any pod name from the list, replace `POD_NAME` with it, and delete it. This is the reconcile loop, live.

```bash
kubectl get pods -l app=web
kubectl delete pod POD_NAME
kubectl get pods -l app=web
```

  </Step>
  <Step title="Feel the missing volume" tone="cyan" checkpoint="After the Redis pod is replaced, the counter starts again at 1. The pod's disk went with it.">

Redis here has no persistent storage, so its data lived and died with its pod. Real data needs a PVC (or a managed database).

```bash
kubectl delete pod -l app=redis
kubectl rollout status deployment/redis
kubectl exec deploy/web -- wget -T 5 -qO- http://web
```

  </Step>
  <Step title="Roll out version 2.0" tone="cyan" checkpoint="Old pods are replaced gradually. rollout status ends with a success message. Calling the Service now prints version: 2.0.">

Build a second image with a different version baked in, load it, and tell the Deployment to use it.

```bash
docker build -t hits:2.0 --build-arg VERSION=2.0 .
kind load docker-image hits:2.0 --name hits
kubectl set image deployment/web web=hits:2.0
kubectl rollout status deployment/web
kubectl exec deploy/web -- wget -T 5 -qO- http://web
```

If your port-forward from before dropped, that is normal: the pod it was attached to was replaced. Start it again if you want it.

  </Step>
  <Step title="Break it on purpose" tone="red" checkpoint="One new pod is stuck in ErrImagePull and then ImagePullBackOff, while the three version 2.0 pods keep serving traffic. The events end with a line like 'Back-off pulling image hits:9.9'.">

Point the Deployment at a tag that does not exist. Because we set `maxUnavailable: 0`, Kubernetes refuses to remove a working pod until the new one is ready, so your app stays up.

```bash
kubectl set image deployment/web web=hits:9.9
kubectl get pods -l app=web
kubectl get events --sort-by=.lastTimestamp
```

Read the output top to bottom. Then ask for details of the broken pod (replace `BAD_POD` with its name). Look at the Events section at the bottom.

```bash
kubectl describe pod BAD_POD
```

  </Step>
  <Step title="Roll back" tone="red" checkpoint="rollout undo reports the rollback and rollout status ends with a success message. The broken pod disappears, and the Service answers with version: 2.0 again.">

```bash
kubectl rollout undo deployment/web
kubectl rollout status deployment/web
kubectl exec deploy/web -- wget -T 5 -qO- http://web
```

  </Step>
</Steps>

### Clean up

Stop any `port-forward` terminal with Ctrl+C first.

<Steps>
  <Step title="Delete the cluster" tone="amber" checkpoint="kind get clusters prints no clusters.">

```bash
kind delete cluster --name hits
kind get clusters
```

  </Step>
  <Step title="Delete the images" tone="amber" checkpoint="docker images no longer lists hits.">

The kind node image is large. List it, then remove it by the image ID in the first column. Then delete the `hits` folder.

```bash
docker image rm hits:1.0 hits:2.0
docker image ls kindest/node
```

  </Step>
</Steps>

## Troubleshooting

Check the pod's status first: see [Reading pod status](#reading-pod-status).

<TroubleGroup title="Running on Kubernetes">
  <Trouble
    symptom="kubectl exec ... wget times out straight after a rollout"
    cause="A Service takes a moment to forget a pod that has just left, so one request can be sent to a pod that no longer exists. It clears by itself once the routing rules catch up. The -T 5 in our command is what stops this hanging for two minutes."
  >

Run the same command again. If every attempt fails, check that the Service has healthy pods behind it.

```bash
kubectl get endpointslices -l kubernetes.io/service-name=web
kubectl get pods -l app=web
```

  </Trouble>
  <Trouble
    symptom="The connection to the server localhost:8080 was refused - did you specify the right host or port?"
    cause="kubectl has no cluster to talk to. Either no cluster exists yet, it was deleted, Docker is stopped (kind nodes are containers), or kubectl points at the wrong context."
  >

```bash
docker ps
kind get clusters
kubectl config get-contexts
kubectl config use-context kind-hits
```

If the cluster is missing, recreate it with the `kind create cluster` step.

  </Trouble>
  <Trouble
    symptom="web pod status: ErrImagePull, then ImagePullBackOff"
    cause="The node tried to download the image and failed. In this tutorial that means the image was never loaded into kind, or the tag is misspelled. 'Back-off' means Kubernetes is waiting longer between tries."
  >

Read the exact reason in the Events at the bottom of `describe`. Then fix the tag or load the image.

```bash
kubectl describe pod POD_NAME
kind load docker-image hits:1.0 --name hits
```

If `kind load` itself errors, save the image to a file and load that instead.

```bash
docker save hits:1.0 -o hits.tar
kind load image-archive hits.tar --name hits
```

  </Trouble>
  <Trouble
    symptom="ErrImageNeverPull"
    cause="The pod uses imagePullPolicy: Never, so Kubernetes will only use an image already on the node, and it is not there."
  >

Load the image into the cluster, or switch the policy back to `IfNotPresent` in the YAML and apply again.

```bash
kind load docker-image hits:1.0 --name hits
kubectl apply -f k8s/web.yaml
```

  </Trouble>
  <Trouble
    symptom="CrashLoopBackOff"
    cause="The container starts, exits and is restarted over and over, with growing waits. The cause is inside the app: a crash, a missing setting, or a failed connection."
  >

Read the logs of the crashed attempt, not the new empty one.

```bash
kubectl logs POD_NAME --previous
kubectl describe pod POD_NAME
```

  </Trouble>
  <Trouble
    symptom="Pending, and the event says: 0/3 nodes are available: 3 Insufficient memory"
    cause="The scheduler cannot find a node with enough free resources to satisfy the pod's requests. On a laptop this is often Docker's memory allowance being too small for three nodes."
  >

Check what the event says exactly, then lower the requests in the YAML or give Docker more memory (Docker Desktop settings, Resources). Also look for a taint or label mismatch if the event says so.

```bash
kubectl describe pod POD_NAME
kubectl describe nodes
```

  </Trouble>
  <Trouble
    symptom="Reason: OOMKilled, Exit Code: 137"
    cause="The container used more memory than its limit, so the kernel killed it. Exit code 137 means it was killed by a signal."
  >

Find it in `describe`, then raise the memory limit or fix the memory use.

```bash
kubectl describe pod POD_NAME
```

Edit `limits.memory` in `k8s/web.yaml` and apply it again.

  </Trouble>
  <Trouble
    symptom="Readiness probe failed: HTTP probe failed with statuscode: 503"
    cause="The app answered, but with an error, or it was not listening yet. For readiness this only removes the pod from the Service. For liveness, repeated failures restart the container."
  >

Check the path, the port and the app's logs. The probe has to hit a URL that really exists.

```bash
kubectl describe pod POD_NAME
kubectl logs POD_NAME
```

If the failure says connection refused during start-up, raise `initialDelaySeconds` or add a startup probe.

  </Trouble>
  <Trouble
    symptom="error: lost connection to pod"
    cause="port-forward is attached to one specific pod. When that pod is replaced during a rollout, restart, or crash, the tunnel breaks."
  >

Run the command again. It picks a pod that exists now.

```bash
kubectl port-forward service/web 8081:80
```

  </Trouble>
  <Trouble
    symptom="bind: address already in use"
    cause="An earlier port-forward is still running in another terminal, or another program uses that port."
  >

Stop the old one with Ctrl+C, or choose another local port such as `8082:80`.

  </Trouble>
</TroubleGroup>

### A debug routine for any pod that is not running

Whatever the status says, work through the same five checks in order. Most problems show up in the first two.

<Flow
  steps={[
    { title: "get pods", note: "What is the status?", tone: "blue", icon: <Eye /> },
    { title: "describe", note: "Read Events at the bottom", tone: "violet", icon: <Search /> },
    { title: "logs", note: "What did the app say?", tone: "green", icon: <ScrollText /> },
    { title: "logs --previous", note: "What did the last crash say?", tone: "amber", icon: <ScrollText /> },
    { title: "exec", note: "Look inside and test", tone: "pink", icon: <Terminal /> },
  ]}
/>

```bash
kubectl get pods
kubectl describe pod POD_NAME
kubectl logs POD_NAME
kubectl logs POD_NAME --previous
kubectl exec -it POD_NAME -- sh
```

<Callout kind="tip">

Modern images (distroless, chainguard) often have no shell, so `exec ... sh` fails. Attach a throwaway debug container that shares the pod's processes instead: `kubectl debug -it POD_NAME --image=busybox --target=CONTAINER_NAME`.

</Callout>
